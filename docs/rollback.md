# Backup, Recovery and Rollback

Applying the session upload-progress mitigation requires an explicit PHP CLI executable and a matching loaded `php.ini`. The tool backs up the complete existing configuration, calculates its SHA-256, records metadata, writes a transaction record, checks for out-of-band changes, atomically replaces the selected file, and checks the selected CLI's effective setting.

The default state directory is `~/.php2shell-fix/`. Its parent must already exist and have trusted ownership and permissions. Existing state is validated, never silently repaired. Linux requires the executing owner and no group/other access for the state, records and backups. Ancestors must be owned by that user or root and not writable by other users, except root-owned sticky directories such as `/tmp`. Windows creates new state atomically with a protected current-user DACL and validates existing owners, DACL grants and ancestor deletion/control rights. SYSTEM, Administrators and Windows servicing are trusted authorities. Reparse points, symlinks and hard-linked recovery files are refused. Backup IDs are 32-character lowercase hex values. Backups and metadata can contain sensitive information; never publish them.

On Linux, replacement preserves UID, GID, permission bits and enumerated extended attributes, including POSIX ACLs and SELinux labels, then verifies the replacement metadata before rename. Unsupported or unreadable metadata fails closed. Hard-linked targets, special mode bits and content-integrity attributes (`security.ima`/`security.evm`) require manual/vendor-managed changes and are refused. Windows uses `ReplaceFileW` to retain the destination DACL; this preview does not attest preservation of target owner/group/SACL or all filesystem metadata. Mutation on other operating systems is refused. Filesystem timestamps and inode identity are not preserved.

```bash
php2shell-fix --rollback BACKUP_ID
```

Before reading recovery data, rollback validates the state, record and backup ownership, permissions and links. It then checks the backup digest and current configuration against the applied digest. On Linux, metadata must also match the recorded original metadata; legacy records lacking this metadata require manual recovery review. SHA-256 detects corruption but does not authenticate data supplied by an untrusted writer. Independently edited content or metadata is not overwritten. After rollback, restart the relevant worker using your deployment procedure and verify application health. Configuration rollback does not undo PHP installation, extension, service or vendor package changes.

If an operation was interrupted, inspect the target `php.ini` and transaction JSON/backup first. Both a state `.lock` and an adjacent `php.ini.php2shell-fix.lock` prevent overlapping tool operations, including operations using different state directories. Never delete an active lock or blindly overwrite newer configuration. Coordinate other administrative writers: identity/content/metadata are rechecked before replacement, but a hostile process with the same user or administrator privileges is outside this protection boundary. If the host crashed after applying mitigation but before report update, reconcile backup/target evidence before manual recovery.
